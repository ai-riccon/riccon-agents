# 设计

## 1. 目标

一个**有界自治**的智能体团队：把一个软件想法从零推进到可用、可验证的增量。用户只做关键决策；其余由团队负责并记录理由。

这不是“任何软件项目都能完全自主交付”的承诺。团队的通用性是**方法级**的：项目合同提供技术栈、命令、工具和约束。能力会随领域和结果的可验证程度而变化。

## 2. 范围

初始范围：

- Web 应用（SaaS、内部工具）、API 服务、CLI、静态站点和自动化。
- T1 bug 修复、T2 加功能、T3 0→1 MVP、T4 认证/支付/PII/迁移/生产关键。
- 以绿地项目为主。现有项目走只读接管路径（M3）。

后续范围：移动端、桌面、嵌入式、数据/ML 和强合规系统。这些需要不同的验证链；不要假装它们有同等深度。

## 3. 团队形状

5 个核心角色：

| 角色 | 负责 | 不写 |
|---|---|---|
| Lead | 合同、状态、计划、门禁、决策、交接 | 生产源码 |
| Product | 目标、用户、MVC、验收标准、UX 流程、文案 | 生产源码 |
| Architect | 技术栈、架构、数据模型、契约、ADR、脚手架 | 功能代码 |
| Builder | 生产源码、测试、迁移、代码级文档 | 决策、合同 |
| Verifier | 独立验收/E2E 测试、评审报告、证据 | 生产源码 |

Ops 按需：CI/CD、容器、部署、可观测性、回滚。

只有 Lead 能 spawn subagent 和问用户。只有 Lead 能把模块标记为待评审。任何人不能自我验收。

### 步数上限

| 角色 | steps |
|---|---|
| Lead | 120 |
| Product | 60 |
| Architect | 80 |
| Builder | 160 |
| Verifier | 100 |
| Ops | 80 |

M2 的两个 Builder 都在 80 步达到上限；M2.1 将 Builder 提高到 160，并同步提高 Lead/Verifier/Architect。`riccon doctor` 会检查每个角色的 `steps` 不低于当前下限。

## 4. 决策权

用户拥有：

1. 产品：目标用户、MVC、non-goals、成功指标。
2. 体验：方向、品牌约束、在原型中做选择。
3. 不可逆/高成本技术选择：无约束时的技术栈、数据模型、公开契约、新增运行时依赖/服务、规模化/安全架构。
4. 交付：生产发布、域名/DNS、云账号、花钱。
5. 风险：安全/合规例外、破坏性操作。

团队拥有常规架构、库选择、重构、测试、文档和任务排序。

## 5. 流程

```text
intake → contract → MVC → build → independent verify → gate → review packet
      → user veto window → next module → ... → release → operate/retro
```

模块是带用户可见结果的纵向切片。依赖完成且前一个 gate 通过后，模块才能开始。MVC 是第一个模块：一条关键旅程，端到端。

## 6. 自治刹车

- 模块评审包；24h veto 窗口；T1–T3 可逆决策沉默即继续。
- 最多连续自动解锁 2 个模块；然后强制方向检查点。
- 墙钟限制：每模块 8h，每 MVC 3 天（M1 后校准）。
- 不设 token 上限；成本可见，但不硬停。
- T4、生产、花钱和破坏性操作永远需要明确 yes。

## 7. 质量

DoD 随轨道变化。T3/MVC 需要验收、构建、测试、关键 E2E、可访问性、安全基线、性能预算、迁移回滚、文档、证据和独立签字。T4 增加威胁建模、负载测试、容灾和明确发布批准。

执行零个测试的测试命令是失败。retry 不能掩盖 flake。verifier 写 review；作者不写。

## 8. 记忆

`.riccon/` 是执行状态的唯一事实源。会话从状态 + 最新 handoff + 合同开始；以更新状态和 handoff 结束。聊天历史不是记忆。

Lead 在每个模块 gate 完成后、phase 切换、决策/评审包后、会话暂停超过 24h、切换项目/风险/模型或进入 T4/生产批准前写 handoff，并让用户新开 session。输入接近 120K tokens、80/120 steps、60 次工具调用或自动 compaction 一次只是检查点，不是强制 handoff：先判断是否会降低质量或导致返工，不会才切。handoff 前必须具备状态/证据/review/gate 已更新、无半写文件或未完成 subagent、`next` 可直接执行、新会话无需重读旧聊天；否则继续或标 blocked。上下文卫生和成本都低于任务质量；不得为了省钱跳过测试、E2E、独立 review 或证据。Architect/Verifier 的 Haiku 接近 80K 时只在任务边界拆新 subagent。

## 9. 工具

内核是确定性、与栈无关的：状态校验、任务/证据/gate/handoff。它不运行项目测试、不选测试、不生成文档、不包装项目工具。那些来自项目合同。

工具在 `AGENTS.md` 中声明，分 required/optional/fallback。MCP 工具必须在 OpenCode 配置中启用；合同只声明意图和路由。

## 10. 里程碑

- **M0**：内核、schema、CLI、安装器、骨架、文档和测试。
- **M1**：单会话受监督循环：合同 → 任务 → 证据 → 独立 E2E/axe → gate → 评审包 → handoff。
- **M2/M3**：多角色协作、`adopt` 接管、Ops（Docker/runbook/verify/CI）和示例 CI。
- **M4**：发布门禁、sandbox 检查、回滚演练和模型映射。
- **H4/H5**：strict DoD 证据绑定、显式 task scope、成本记录、adopt 多栈、shell 证据解析加固。

公开快照只保留团队内核、模板、测试和公开文档；历史试点报告、审计材料和示例证据不随仓库发布。

## 11. 风险与非目标

- 产品品味和市场判断不能完全外包。
- 瓶颈是验证，不是编码。
- 未知技术栈需要发现，质量可能下降。
- 权限模式不是安全边界；使用一次性运行时。
- 单一模型会限制长程规划；角色映射见 [MODELS.md](./MODELS.md)，需要按组织和模型变化复核。
- “任何项目、完全自主”是非目标。评测集定义团队能诚实声称的范围。
